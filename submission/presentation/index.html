M1

Protocol foundations

M1

No third party holds funds or matches orders.

01

Self-custodial

Each role keeps its own keys, state and recovery authority. Bitcoin custody is a 2-of-2 MuSig2 output neither side can spend alone. The LEZ refund instruction takes no signer at all and can only pay the recorded depositor.

No bridge · no custodian · no third-party signer
02

No liquidity pool

Every swap is bilateral: two parties, and the exact amounts fixed in the countersigned agreement before either chain moves. No pooled capital, no LP position, no pricing curve.

No pool to drain · no shared inventory
03

Peer-to-peer offers

Offers travel as signed envelopes from maker to taker. The taker verifies the maker's signature and the exact terms before consenting to anything. Nothing on that path takes custody or matches orders.

No venue custody · no matching engine
Consequence: recovery never depends on the counterparty's cooperation, on an operator staying online, or on a third party staying solvent. Each side's refund is a transaction it can already build and broadcast itself.

There is no "reveal" step

The Taker never sends t to anyone. It signs a transaction it wanted to send anyway. The signature that made the escrow pay out is the same object the Maker subtracts from — publication is a side effect of getting paid.

Why the Taker cannot sign alone

The aggregate authority is a 2-of-2 MuSig2 key. The Taker holds one partial, never the other. The pre-signature from the signing rounds plus t is the only route to a complete signature under that key.

And it cannot be faked

Extraction returns a scalar only when t·G = T against the T the agreement froze. A different signature yields no scalar or a point mismatch — never a wrong secret that looks usable.

Nothing is transmitted.The Taker gets paid; the Maker reads the receipt.

Nothing is taken on trust

Every account the caller passes is re-derived or compared against the metadata written at initialize. Supplying a different vault, a different claimant, or a partially drained balance fails the same branch.

Authority is the last check

Bindings first, cryptography second. A caller with a perfectly valid signature still cannot claim into the wrong account, and the expensive check never runs on a malformed request.

Versioned on both sides

The escrow stamps version: 2 into every record and refuses the XMR branch unless it reads 3. The agreement carries BTC_AGREEMENT_SCHEMA_V1, and every digest domain ends in /v1.

Addresses need no registry

Both accounts are PDAs of the swap id, so any observer derives them without asking anyone. There is no index to query, no operator to be online, and nothing to gate discovery.

Permissionless ≠ unrestricted

Dropping the signer on refund does not widen who gets paid. The binding still forces the recorded depositor, so a stranger submitting it merely pays the fee on someone else's recovery.

What that buys

Recovery survives the counterparty vanishing, the maker daemon being down, and the taker losing its process. A watchtower — or the counterparty, wanting its own leg unstuck — can push the refund through.

The deadline is enforced by consensus.

                       vec![transfer])

    custody.clone(), depositor.clone(), state.amount, true, &swap_id);

// refund_at is fixed at initialize and never rewritten afterwards.

if … || refund_at == 0 { return Err(…) }   // rejected at init

Disjoint and exhaustive

..refund_at and refund_at.. tile the timeline with no overlap and no gap. Exactly one of claim and refund can be included in any block — the escrow needs no if now < deadline, because a stale transaction is never valid to include.

The maker-funded leg refunds first

Deadlines are staggered in the agreement, not here. The leg funded second carries the earlier refund_at, so the party who moved first is always the last one able to recover.

Not a race with the claim

Because the windows cannot overlap, the LEZ side has no claim-versus-refund contention. That race exists only on Bitcoin, after CSV maturity, and is what the safety margin keeps the normal flow away from.

Key path — the normal case

Both parties sign once under the MuSig2 aggregate. On chain it is a single Schnorr signature against one key: no script, no branch, nothing that says "swap". The refund leaf is never published.

Script path — the recovery case

Only if cooperation fails. OP_CSV enforces a relative block delay against the funding output, then one signature from the funder's own refund key. Revealing the leaf also reveals the control block.

Parity is load-bearing

output_key_parity is carried into the signing context and into the durable binding. It is exactly the field that silently flips and produces a signature that fails much later, so it is committed early and compared on resume.

Bitcoin is not post-quantum either.

  1. Post-quantum atomicity would protect nothing here. The same adversary spends the P2TR output directly — a Taproot output key is on chain from the moment it is funded.
  2. So the mechanism was chosen on properties we can actually have. No script on either chain, no preimage on chain, nothing linking the two legs, one fewer output to spend.
  3. Upgrading is a mechanism swap, not a redesign. ClaimAuthority is per escrow, and Sha256Preimage already runs the ZEC corridor. Agreement, deadlines and refunds do not depend on the signature scheme.
BTC leg · adaptordiscrete log
ZEC leg · BIP-199 hashlockhash — already PQ-shaped
The gap is real: an HTLC's secret is a hash preimage — Grover only halves it, so its atomicity survives. Ours is a scalar with T = t·G published in the agreement, so Shor recovers t and claims both legs. Bitcoin gives us no way to close that today: lattice (LAS) and isogeny (IAS) adaptor signatures exist in research but need a soft fork. Exposure is real-time, not harvest-now — a settled swap cannot be stolen retroactively.
Not a claimed property · tracked as a design assumption, not a mitigation
