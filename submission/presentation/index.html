M1

Protocol foundations

M1

No third party holds funds or matches orders.

01

Self-custodial

Each role keeps its own keys, state and recovery authority. Bitcoin custody is a 2-of-2 MuSig2 output neither side can spend alone. The LEZ refund instruction takes no signer at all and can only pay the recorded depositor.

No bridge · no custodian · no third-party signer
02

No liquidity pool

Every swap is bilateral: two parties, and the exact amounts fixed in the countersigned agreement before either chain moves. No pooled capital, no LP position, no pricing curve.

No pool to drain · no shared inventory
03

Peer-to-peer offers

Offers travel as signed envelopes from maker to taker. The taker verifies the maker's signature and the exact terms before consenting to anything. Nothing on that path takes custody or matches orders.

No venue custody · no matching engine
Consequence: recovery never depends on the counterparty's cooperation, on an operator staying online, or on a third party staying solvent. Each side's refund is a transaction it can already build and broadcast itself.

1Both addresses are the swap id

Metadata at pda = swap_id, the vault at ["custody", swap_id]. Nobody chooses either; both sides — and any observer — derive the same two.

2Only the depositor seeds it

The one signer on the instruction. You cannot lock someone else's balance into a swap they never agreed to.

3The joint key — not T

What is recorded is the aggregate MuSig2 key. The escrow never stores, receives or checks T, and has no idea an adaptor secret exists. It demands one thing: a signature under this key.

4No escrow without terms

Zero amount, missing deadline or unbound terms_hash are refused. The record cannot exist in a state the claim or refund would have to interpret.

5And never self-claimable

valid_claim_authority requires account_id != claimant. A swap whose claimant could claim alone is rejected at seeding — not caught at payout.

6The vault must be empty

A balance already at that address means the swap id has been used. Re-seeding over a live escrow is impossible.

7Written once

Amount, deadline, both parties, custody and the claim authority land in one record and are never rewritten. Every later check reads from here.

So where is T armed?Not in the escrow. Two places, both before this instruction runs.

1The escrow takes no signature argument

It requires the transaction itself to be signed by the aggregate account. No parameter carries s, and none carries t.

2Bindings before cryptography

Eight account checks run first, so a valid signature still cannot claim into the wrong account or against a drained vault.

3Strictly before the deadline

Consensus refuses to include this after refund_at. A late claim is not a race — it is not a valid transaction.

4The signer is the key from creation

Recomputed by hashing, not trusted from the caller. It must equal what initialize wrote.

5…and it is not the claimant

This clause forces a joint signature to exist on chain. Without it the claimant could sign alone and nothing would be revealed.

6Only adding t makes that signature

The claimant holds one MuSig2 partial. The pre-signature plus t is the only complete signature it can produce under the joint key.

7What if the Taker refuses to reveal?

Then it does not get paid. There is no other signature it can build: a fresh MuSig2 session would need the Maker's partial, and the Maker only ever gave a pre-signature. Claiming and revealing are the same act — and after refund_at the escrow returns the LEZ to the Maker.

Nothing is transmitted.The Taker gets paid; the Maker reads the receipt.

Permissionless methods

agreement countersigned→one or both legs locked→no reveal→deadline passes→refund
escrow/src/lib.rs · refund_native — the whole instruction, as an outsider would call it
pub fn refund_native(_ctx: ProgramContext,
    #[account(mut, owner = self_program_id, pda = arg("swap_id"))] metadata, 1
    #[account(mut, pda = [literal("custody"), arg("swap_id")])] custody,
    #[account(mut)] depositor: AccountWithMetadata,    // ← no signer    2
    swap_id: [u8; 32]) -> SpelResult
{
    let mut state = read_metadata(&metadata)?;
    require_funded(&state)?;
    if state.swap_id != swap_id
        || state.asset_program != state.custody_program
        || state.depositor != depositor.account_id                            3
        || state.custody != custody.account_id
        || custody.account.balance != state.amount
    { return Err(custom_error(ERROR_ACCOUNT_BINDING,
        "native refund account binding mismatch")); }

    let transfer = native_transfer_call(state.asset_program, custody.clone(),
        depositor.clone(), state.amount, true, &swap_id);
    state.status = EscrowStatus::Refunded;
    Ok(SpelOutput::execute(…).with_timestamp_validity_window(state.refund_at..)) 4
}

1No registry to consult

Both addresses derive from the swap id, so a watchtower computes them itself — no API key, no index, no cooperation from either party.

2No signer anywhere

The only instruction in the program without #[account(signer)]. Anyone holding the swap id can submit it.

3Still bound to the depositor

Permissionless is not unrestricted. A stranger who submits it pays the fee and moves nobody else's money.

4And only after the deadline

Consensus will not include it earlier, so an outsider cannot pre-empt a live swap. The claim stays closed to outsiders — it needs the joint signature.

5What that survives

Taker offline: anyone recovers its deposit for it. Maker daemon down: the same. Neither outage strands funds, because the recovering transaction needs nothing either party holds.

Key path — the normal case

Both parties sign once under the MuSig2 aggregate. On chain it is a single Schnorr signature against one key: no script, no branch, nothing that says "swap". The refund leaf is never published.

Script path — the recovery case

Only if cooperation fails. OP_CSV enforces a relative block delay against the funding output, then one signature from the funder's own refund key. Revealing the leaf also reveals the control block.

Parity is load-bearing

output_key_parity is carried into the signing context and into the durable binding. It is exactly the field that silently flips and produces a signature that fails much later, so it is committed early and compared on resume.

Bitcoin is not post-quantum either.

  1. Post-quantum atomicity would protect nothing here. The same adversary spends the P2TR output directly — a Taproot output key is on chain from the moment it is funded.
  2. So the mechanism was chosen on properties we can actually have. No script on either chain, no preimage on chain, nothing linking the two legs, one fewer output to spend.
  3. Upgrading is a mechanism swap, not a redesign. ClaimAuthority is per escrow, and Sha256Preimage already runs the ZEC corridor. Agreement, deadlines and refunds do not depend on the signature scheme.
BTC leg · adaptordiscrete log
ZEC leg · BIP-199 hashlockhash — already PQ-shaped
The gap is real: an HTLC's secret is a hash preimage — Grover only halves it, so its atomicity survives. Ours is a scalar with T = t·G published in the agreement, so Shor recovers t and claims both legs. Bitcoin gives us no way to close that today: lattice (LAS) and isogeny (IAS) adaptor signatures exist in research but need a soft fork. Exposure is real-time, not harvest-now — a settled swap cannot be stolen retroactively.
Not a claimed property · tracked as a design assumption, not a mitigation
